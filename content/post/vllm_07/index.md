## 显存消耗
vllm启动的时候会查看Free memory,比如我的RTX 2060s 8G跑Qwen3.5:2B模型时，vllm启动有打印
**Free memory on device(7.51/7.6GiB) **，这里7.6G是cuda能看到的总显存，差的是驱动内部扣留（NVIDIA 驱动模块、页表、内部 buffer、cudagraph/模块加载预留等。这部分 nvidia-smi不归到任何进程头上（per-process 列表里只有 Xorg 的 4 MiB），所以看起来"凭空消失"）。7.51G又比7.6G少了一些，这是 torch 初始化 CUDA context、cuBLAS workspace 占掉的，这7.51G就是vllm可用的了。

### 常驻占用分类（运行稳态）
| 类别 | 大小 | 说明 |
|---|---|---|
| 权重（fp16） | ≈ 4.2 GiB | 模型文件实测 4.24 GiB（含 MTP 层） |
| 非 torch（CUDA context、cuBLAS、运行时） | ≈ 0.3 GiB | 日志把两者合并报为 4.51 GiB |
| KV cache | 0.98 GiB | util=0.95 时；随 util 变化：0.85→0.22，0.90→0.60 |
| CUDA graph 池 | 0.06 GiB | 解码图捕获的图池 |
| 运行激活/工作区（常驻部分） | ≈ 0.13 GiB | 倒推：5.68 − 4.51 − 0.98 − 0.06 |

 ### 非常驻口径（只参与预算计算，不常驻）
| 类别 | 大小 | 说明 |
|---|---|---|
| 峰值激活 | 1.74 GiB | profiling 阶段测出的 prefill 峰值激活，之后释放，只用来算 KV 预算 |

### vllm推理的显存要求
  vllm推理大模型的刚性成本 ≈ 4.51 + 1.74 + 0.06 ≈ 6.3 GiB——这解释了之前测试的发现：gpu-mem-util 低于 ~0.85 时 KV cache 趋近于 0（case 3:
  util=0.85 时 KV 只剩 0.22 GiB）。

  KV cache = util × 总显存 − 权重 − 峰值激活 − cudagraph 池
          = 0.95 × 7.6 − 4.51 − 1.74 − 0.06 ≈ 0.88 GiB

  KV cache 不是固定大小，是"剩多少给多少"。

### --gpu-memory-utilization
设置 vLLM 实例占用的 GPU 显存比例，直接作用于cuda查出来的显存总容量，默认 0.9。该参数是一个硬性预留，如果 GPU 上已有其他进程占用，即使占用很小，vLLM 也可能因无法满足预留而拒绝启动。比如8G显存，该参数设置为0.9，其他进程占用了1G，剩余7G小于8*0.9=7.2G，就会因为OOM导致vllm启动失败。
此参数首先作用于启动vllm时刻的可用显存，首先不许满足启动模型的刚性需求，否则直接启动失败，此参数设置越大，kv cache可用空间越多。但是不能设置为1，否则也会启动失败。
因为即使模型权重和 KV Cache 已经分配完毕，推理过程中仍会产生动态显存开销，包括 CUDA Graph 录制、PyTorch 框架自身的临时分配、内存碎片等。如果 vLLM 占用了 100% 的显存，这些运行时开销将无处安放，必然导致 OOM

### --max-model-len
此参数表征模型的最大序列长度（输入+输出）。
vLLM 启动时预留 KV Cache 的核心规则是：必须能容纳至少一个完整的 max_model_len 长度的请求。也就是说如果剩余的显存无法满足一个请求的max-model-len长度的kv cache，那就报OOM，进而启动失败。

### --max-num-seqs

此参数不直接决定启动时预留的 KV Cache 大小，但会在运行时通过激活值、CUDA Graph 等开销间接影响显存，设置过大同样会导致 OOM。从上表可以看出，不过此值比较影响吞吐量

### --enforce-eager 
eager=1 省掉 cudagraph 池，KV cache 微升（1.03 vs 0.98GB），但吞吐 176 vs 361 tok/s（-51%）、TTFT 1117 vs 612ms（×1.8）。

### --max-num-batched-tokens
此参数默认为8192，case 11 提到 16384 后：峰值激活翻倍 → KV cache 被挤到 0.22GB（vs case 8 同参数下的 0.61GB），总显存反而降至 5.47GB，吞吐也下降（243 vs 319 tok/s）。
这个默认上限是"max-model-len × max-num-seqs 影响显存"的开关：只有把它放大，这两个参数才会通过激活内存影响显存占比。

### 结论

8GB 卡跑 Qwen3.5-2B：**显存占比几乎只由 gpu-mem-util 决定**（推荐 0.90~0.95）；max-model-len / max-num-seqs 不改变显存预留（受默认 8192 批上限保护），它们影响的是调度与性能；enforce-eager 仅建议在 cudagraph 有兼容性问题时使用。全程无 OOM。
